== Narrow float types

[quote]
____
`f16`, `bf16` and the two `fp8` encodings are scalar value types. +
Each one is a C type the type layer recognises and lowers to an `OpTypeFloat` with the width and floating-point encoding SPIR-V asks for. +
The family shares one rule: the type is a carrier. What an operation may emit depends on the encoding, not on the C spelling. +
Precision, range and the corner cases are the ones of the encoding; nothing is silently widened.
____

[cols="1,2,2,3",options="header"]
|===
| family | C spelling | SPIR-V type | declared by the type layer
| f16 | `_Float16` | `OpTypeFloat 16` | `Float16` capability
| bf16 | `__float128` + `annotate("__bf16")` | `OpTypeFloat 16 BFloat16KHR` | `BFloat16TypeKHR` capability, `SPV_KHR_bfloat16` extension
| fp8 E4M3 | `__float128` + `annotate("__fp8_e4m3")` | `OpTypeFloat 8 Float8E4M3EXT` | `Float8EXT` capability, `SPV_EXT_float8` extension
| fp8 E5M2 | `__float128` + `annotate("__fp8_e5m2")` | `OpTypeFloat 8 Float8E5M2EXT` | `Float8EXT` capability, `SPV_EXT_float8` extension
|===

`bf16` and `fp8` have no C keyword. They are carried by `__float128` and named by an annotation on the typedef: the type layer reads the first annotation containing `__bf16` / `__fp8_e4m3` / `__fp8_e5m2` and replaces the width and the encoding of the carrier with it. A type without such an annotation stays an unsupported 128-bit float.

* the annotation spelling also accepts `__nv_bfloat16`, and `__f8_e4m3`, `__nv_fp8_e4m3`, `__f8_e5m2`, `__nv_fp8_e5m2`.
* the capability and the extension are added on first use of the type, so a module that never names an `fp8` type never declares `SPV_EXT_float8`.
* the encoding lives in the type: an `OpFConvert` between two fp8 encodings is one instruction, and an fp8 value never decays to `f32` on its own.

=== conversions

Every conversion is an ordinary SPIR-V conversion on the narrow type; the family is not staged through `f32`.

[cols="1,2",options="header"]
|===
| from -> to | emitted
| float -> float (any width / encoding) | `OpFConvert`; in a constant context `OpSpecConstantOp` `FConvert`
| integer -> float | `OpConvertSToF`
| float -> integer | `OpConvertFToS`
| float -> `bool` | `OpFOrdNotEqual` against zero
| `bool` -> integer / float | `OpSelect`
| same type | nothing, the value is reused
|===

* the fp8 encodings take `OpFConvert`, `OpConvertSToF` and `OpConvertFToS` like any other float.
* an fp8 type has no comparison instruction: a comparison on it is rejected, and a boolean context (`if (v)`, a float -> `bool` conversion) has no lowering.
* C's usual arithmetic conversions still decide the operation's type: an `f16` operand combined with a `float` operand promotes the operation to `f32`, and the assignment converts back with `OpFConvert`. Two operands of the same narrow type stay on that type (`OpFAdd %half`, not a widened add).
* a conversion in a constant context is folded on the host and emitted as an `OpConstant` of the destination type, never as a conversion instruction.

=== literals

A cast of a literal to a narrow float is folded on the host: the value is encoded with the bits of the destination, and the module gets an `OpConstant` of that type. No `OpFConvert` is emitted for it.

[cols="1,1,1,1,1",options="header"]
|===
| value | f16 | bf16 | fp8 E4M3 | fp8 E5M2
| 0.5 | 0x3800 | 0x3F00 | 0x30 | 0x38
| 1.0 | 0x3C00 | 0x3F80 | 0x38 | 0x3C
| 3.0 | 0x4200 | 0x4040 | 0x44 | 0x42
| largest finite | 0x7BFF | 0x7F7F | 0x7E (448) | 0x7B (57344)
| infinity | 0x7C00 | 0x7F80 | none, 0x7F is NaN | 0x7C
|===

* **f16** is IEEE binary16. Rounding is truncation toward zero, so `65535` still lands on `65504` (`0x7BFF`) and `65536` becomes an infinity (`0x7C00`).
* **bf16** is the truncated high half of the binary32 image of the value. It has the exponent range and the rounding of `f32`, 8 bits of mantissa, and no overflow for a finite `f32` input.
* **fp8 E4M3** has no infinity. The largest finite value is 448 (`0x7E`); the all-ones pattern (`0x7F`) is NaN. Out-of-range values saturate to 448, `f32` subnormals and anything below the smallest E4M3 subnormal flush to a signed zero, infinities and NaNs become `0x7F`. Rounding is truncation.
* **fp8 E5M2** is IEEE-754 with a 5-bit exponent and a 2-bit mantissa: it has infinities and NaNs, and it does not saturate. Rounding is truncation toward zero (`60000` lands on `57344`), and a value that truncates past the top of the range becomes an infinity (`0x7C`).

=== arithmetic and comparison

[cols="2,1,1,1",options="header"]
|===
| operation | f16 | bf16 | fp8 (both encodings)
| `+` `-` `*` `/` `%` | native `OpFAdd` / `OpFSub` / `OpFMul` / `OpFDiv` / `OpFMod` on the narrow type | native through `SPV_EXT_bfloat16_arithmetic` | rejected
| unary `-` | native, `OpFSub` from zero | native, same | rejected
| `<` `<=` `>` `>=` `==` `!=` | native `OpFOrdLessThan` and friends | native through `SPV_EXT_bfloat16_arithmetic` | rejected
|===

* `SPV_EXT_float8` defines no arithmetic and no comparison at all, so an fp8 operation is a hard compile error (`ACLSPV_COMPILE_UNHANDLED_CARVE`). It is rejected instead of being silently widened to `f32`, which would change the precision the type was chosen for.
* bf16 arithmetic and comparison are native when `ACLSPV_BF16_ARITHMETIC` is on (default). The library then declares `SPV_EXT_bfloat16_arithmetic` and `BFloat16ArithmeticEXT` on first use. With the switch off, bf16 arithmetic and comparison are rejected exactly like fp8.
* f16 arithmetic needs only the `Float16` capability the type layer already added.

=== builtin math

* <<__builtin_sinf16,__builtin_sinf16>>, <<__builtin_cosf16,__builtin_cosf16>> and <<__builtin_tanf16,__builtin_tanf16>> emit `GLSL.std.450` `Sin` / `Cos` / `Tan` (13 / 14 / 15) with a 16-bit operand and result.
* a literal operand is folded on the host into a binary16 `OpConstant`, because an extension instruction is not a legal `OpSpecConstantOp`. This is gated by `ACLSPV_MATH_LITERAL` (default on).
* `bf16` has no `GLSL.std.450` lowering: a literal operand folds, a runtime operand is rejected with `ACLSPV_COMPILE_UNHANDLED_CARVE`.
* fp8 has no math builtin and no `GLSL.std.450` lowering.
* the `__builtin_elementwise_*` family is 32-bit (`f32`) by specification, see <<__builtin_elementwise_sin,__builtin_elementwise_sin>>; a narrow operand is converted to `f32` for the call.

=== shapes and limits

* f16 is the only member with a full vector form: `ext_vector_type` over `_Float16` emits `OpTypeVector` of half and elementwise arithmetic on it.
* bf16 and fp8 are scalar types here; a vector of them is not a supported shape.
* a block-scope object can be declared only for f16 (`const f16 h = 1.0f;`). A `bf16` or `fp8` variable declaration is rejected with `ACLSPV_COMPILE_MET_INVAL_TYPE_NOT_KNOWN`; use parameters, pointees, function results and cast expressions instead.
* a function may return a bf16 or fp8 value.
* storage class annotations and the entry point rules are the ordinary ones, see <<attributes,Attributes>>.

=== configuration

The family is compiled in, and can be compiled out, per type. Each switch is a CMake cache variable (for example `cmake -S. -Bbuild -DACLSPV_SCLR_F8_E5M2=0`).

[cols="2,1,3",options="header"]
|===
| switch | default | effect
| `ACLSPV_SCLR_F16` | 1 | the f16 id and `OpTypeFloat 16`
| `ACLSPV_SCLR_BF16` | 1 | the bf16 id and its encoded type
| `ACLSPV_BF16_ARITHMETIC` | 1 | native bf16 arithmetic and comparison through `SPV_EXT_bfloat16_arithmetic`; when 0 they are rejected
| `ACLSPV_SCLR_F8_E4M3` | 1 | the E4M3 id and `OpTypeFloat 8 Float8E4M3EXT`
| `ACLSPV_SCLR_F8_E5M2` | 1 | the E5M2 id and `OpTypeFloat 8 Float8E5M2EXT`
| `ACLSPV_TYPE_FLOAT_ALIAS` | 1 | the annotation spellings for bf16 and fp8; when 0, `__float128` stays unsupported
| `ACLSPV_MATH_LITERAL` | 1 | host folding of the math builtins' literal operands
|===

* each test directory (`test/comp-f16`, `test/comp-bf16`, `test/comp-fp8`) is only registered when the types it exercises are enabled.
* when a width has to be named without an encoding, 8 bits fall back to E4M3 and 16 bits to f16 (`ACLSPV_ID_F8_OR_Z`, `ACLSPV_ID_F16_OR_Z`).

=== Inline and destructors

[quote]
____
Call-site inlining is not enabled for ordinary calls yet. Destructor bodies are
inlined only where the language model requires it, namely subobjects.
____

* a destructor of a whole local object is an ordinary function call
  (`OpFunctionCall`).
* a subobject (a struct member, an array element, or a member selected through a
  pointer) cannot be passed as an `OpFunctionCall` pointer argument in SPIR-V
  logical addressing. its destructor body must be inlined.
* therefore, subobject destruction is only supported when the destructor is
  inlinable. a member function defined inside its class body is implicitly
  inline; an out-of-class definition must say `inline` or `always_inline`.
  a non-inline destructor is still valid for a whole object, but struct members
  and array elements whose destructor is not inlined are not usable in this
  language model.
* `noinline` is a hard rejection for a subobject destructor: the compiler cannot
  form the required pointer argument and must not silently skip the destruction.

=== ExportAttributes

[quote]
____
Some functions are meant to leave the module: a linker resolves them, not this translation unit. +
These are ordinary clang attributes, not <<AnnotationAttributes,annotations>>.
____

[cols="1,2",options="header"]
|===
| attribute | meaning
| `__declspec(dllexport)` | the function is exported
| `__attribute__((visibility("default")))` | the function is exported
| `__attribute__((visibility("hidden")))` | the function is not exported by the export-by-default policy
|===

* a function is exported when it says so explicitly, or when the export-by-default policy is on and it is not `visibility("hidden")`. an explicit export wins over `hidden`.
* an exported definition gets `OpDecorate %fn LinkageAttributes "<name>" Export`, and the first export adds the `Linkage` capability.
* the symbol name is clang's mangled name (`clang_Cursor_getMangling`), with the source spelling as fallback. C declarations and `extern "C"` declarations therefore keep their plain name; C++ declarations carry their Itanium name. `OpName` and `LinkageAttributes` use that one string, so a module's display name and its symbol name never diverge.
* entry points use the same naming rule in `OpEntryPoint`. a C++ entry point is therefore listed by its mangled name; declare it `extern "C"` when a stable source-level name is wanted, and the compiler emits a warning when the two differ.
* internal-linkage functions (`static`) are kept in a separate cache and are never imported or exported. their lookup key is the cursor USR, not the display name: two static entities may share one plain C name.
* only a definition with a body is exported: a declaration alone has nothing to export yet.
* entry points are not exported. they are reached through `OpEntryPoint`, not through linkage.
* `ACLSPV_CTX_FLAG0_EXPORT_BY_DEFAULT` turns the policy on: every defined function is exported unless it is `visibility("hidden")`. use it when this module is one part of a larger linked program.
* the opposite direction is an import: a called function that is declared without a body in this translation unit is declared `LinkageAttributes "<name>" Import`, before every definition in the module.

++++
<div class="listingblock" style="background-color:#1c171b;color:#d8ccd3;padding:0.8em 1em;overflow-x:auto;border-radius:4px">
<pre style="font-family:'Source Code Pro','DejaVu Sans Mono','Courier New',monospace;font-size:14px;line-height:1.3;margin:0;background:transparent;color:inherit">/** exported explicitly */

=== FunctionControlAttributes

[quote]
____
The `OpFunction` control mask is read from the declaration when the function is emitted. +
It is a hint for a downstream inliner; this compiler emits the declaration as written.
____

* `__attribute__((always_inline))`, or the `inline` keyword where the language mode has it, emits `Inline`.
* `__attribute__((noinline))` emits `DontInline`. when both are present, `noinline` wins.
* a defined body is analysed: one that writes no state it does not own emits `Pure`, and one that also reads none emits `Const` (`Const` implies `Pure`).
* a body-less declaration has nothing to analyse: its `__attribute__((pure))` / `__attribute__((const))` is what the declaration carries.
* without any of these, the mask is `None`. an entry point always carries `None`.

entry point

[quote]
____
is a void (void); with interface attached. +
you can have multiple entry points in a shader. (you can have vertex & frag shader at one go!) +
in aclang the entry point is very flexible since execution mode & objects are represented as attributes & arguments.
____

arguments

[quote]
____
unlike normal function, arguments of entry point have different meaning. +
for pointers with <<aclspv_storage_class,storage class>> will be a variable declared globally binded. +
a push-constant argument is a pointer to a struct with `aclspv_storage_class(9)`: it gets its own `PushConstant` variable, so the block layout and its padding belong to that argument alone. +
a `const` pointee marks a storage buffer or storage image `NonWritable`, so a read-only resource is usable in the vertex stage without the `vertexPipelineStoresAndAtomics` feature. +
without `storage class` specified on pointer parameter, compiler should emit an error.
____

bindables

[quote]
____
every entry points have its own reserved <<aclspv_set,descriptor set>>, incremented from 0. +
from left to right, bindable arguments have its reserved <<aclspv_bind_idx,binding index>> from 0, incremented on every bindable obejcts.

== Builtin

[quote]
____
Builtin expressions recognised while carving. +
Unlike <<attributes,Attributes>>, they are not annotations: they use ordinary call syntax (or a vector expression) and are emitted as SPIR-V instructions.
____

[[__builtin_sinf]]
=== __builtin_sinf

[quote]
`__builtin_sinf(x)`

* emits `GLSL.std.450` `Sin` (instruction 13).
* scalar only: operand and result are 32-bit floating point (`f32`).
* the operand is cast to the result type before the call is emitted.
* passing a vector is a clang type error, so this spelling never yields a vector.
* a scalar literal operand is folded on the host into an `OpConstant` instead of `OpExtInst`, because an extension instruction cannot appear in `OpSpecConstantOp`.
* `f64` (`__builtin_sin`) is not supported for now.
* the bare `sinf` name is not recognised; only the `__builtin_` spelling is.

== Statement expression

[quote]
____
GNU statement expression `({ statement; ...; expression; })` is an ordinary expression. +
Its statements are carved into the current block, and the value of the last expression is the value of the block.
____

* the block is emitted where the expression appears, so its side effects keep source order.
* declarations inside the block are function-scoped variables, like any other declaration of the enclosing function.
* control flow in the block (`if`, `while`, ...) is carved as usual; the value expression comes after it, in the merge block.
* statement expressions may nest: each nested block evaluates with its own expression scratch, restored in LIFO order.
* the block's value is a runtime operand. It is not constant-folded, even when its last expression is a literal.
* a block whose last statement is not an expression is rejected with `ACLSPV_COMPILE_UNHANDLED_BODY_STMTEXPR`.

== Restriction

[quote]
Some statements / extensions may not be planned to be supported for now.

* `VK_KHR_relaxed_block_layout` behaviour (free alignment)
* Non plain-old-data types
* `OpenCL` memory model
* `function-scoped variable` shadowing function parameter
* designated initializer list
* pointer arithmetic on non-physical addressing model
* global variables
* pointer to struct on input | output buffer
* recursion, direct or mutual: the call graph must be acyclic. a cycle is reported as `ACLSPV_COMPILE_RECURSIVE_CALL` instead of emitted, because SPIR-V has no recursive `OpFunctionCall`.
* `bf16` and `fp8` block-scope variables: those types exist as parameters, pointees, function results and expression values, see <<narrow-float,narrow float types>>.
* arithmetic, comparison and math on `fp8`: the encodings define no such instructions, see <<narrow-float,narrow float types>>.
